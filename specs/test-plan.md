# Тест-план приложения «Пора на ТО»

## 1. Цель и границы

План задаёт проверку общего Kotlin Multiplatform-приложения для Android и iOS: бизнес-логики, локальной базы, Compose UI, платформенных уведомлений, приватности и безопасности.

Проверяется реализованный функционал и согласованные требования из `specs/` и `dev_plan.md`, включая функции этапов 8б и 9. Нереализованные идеи не считаются частью приёмки, пока не утверждены продуктовые решения. Открытые дефекты не принимаются за ожидаемое поведение: после исправления для них добавляется регрессионный тест.

План не заменяет требования магазинов приложений, аудит инфраструктуры или анализ серверной части. В текущей архитектуре данные хранятся локально; сетевые сценарии не предполагаются.

## 2. Тестовая стратегия

Использовать пирамиду тестирования: много быстрых общих тестов domain-логики, интеграционные тесты локального хранилища и адаптеров, затем меньшее число UI/E2E сценариев. Один и тот же бизнес-результат не нужно повторять на каждом уровне.

| Уровень | Что проверяется | Среда |
|---|---|---|
| Unit, `commonTest` | Use case-ы, вычисления, сортировка, нормализация, даты, преобразование единиц, планирование напоминаний | Kotlin Multiplatform common tests |
| Data integration | SQLDelight-запросы, мапперы, реактивные Flow, транзакции, удаление и миграции | In-memory SQLite/тестовый SQLDelight driver; platform driver там, где поведение зависит от платформы |
| Presentation | ViewModel состояния, события, валидация, загрузка/ошибки/пустые состояния | Общие тесты с fake repositories и тестовым временем |
| UI | Семантика, ввод, диалоги, состояния экранов, переходы | Compose UI tests в `commonTest` (`runComposeUiTest`, базовый класс `UiTest`): на Android — Robolectric в host-тестах, на iOS — симулятор; XCTest для iOS host-интеграции при необходимости |
| E2E и ручной smoke | Сквозные пользовательские потоки и системные интеграции | Android Emulator, iOS Simulator и физические устройства |
| Security automation | Секреты, зависимости и статические находки в коде/конфигурации | CI на каждом Pull Request и перед релизом |

Для тестов с датой, временем и корутинами использовать управляемые часы и тестовый coroutine scheduler; не зависеть от текущей даты, локального часового пояса или реального ожидания уведомления.

|---|---|---|
| DOM-01 | Рассчитать статус работы по пробегу: далеко до срока, граница окна напоминания, срок наступил, срок пройден | `OK`, `SOON`, `DUE` соответствуют согласованным границам; остаток и прогресс корректны |

| DOM-03 | Сравнить статус по километрам и времени | Итоговый статус выбирается по более срочной оси |
| DOM-04 | Проверить даты на границах месяца/года, високосный день и неполный месяц | Результат совпадает с календарными правилами domain-спецификации |
| DOM-05 | Нормализовать новую работу с явным и отсутствующим окном напоминания | Сохраняются допустимые значения и применяется согласованное значение по умолчанию |
| DOM-06 | Добавить, изменить, удалить авто/работу; изменить пробег и настройки | Use case корректно делегирует операцию и обрабатывает отсутствующую сущность/отказ репозитория |
| DOM-07 | Отметить работу выполненной и снять отметку | Создаётся/удаляется связанная запись; состояние работы возвращается к значениям до отметки согласно правилам предметной области |
| DOM-08 | Изменить запись истории, являющуюся отметкой работы | Работа перемещается на новый пробег только если её не меняли после отметки; обычная запись не изменяет работу |
| DOM-09 | Планировать уведомления при выключенном push, статусах `OK`/`SOON`/`DUE`, недавнем уведомлении и прошедшем времени напоминания | Соблюдаются окно планирования, антиспам и настройки пользователя |
| DOM-10 | Отсортировать работы и историю, сформировать car alerts | Порядок, счётчики и пустые наборы корректны и детерминированы |
| DOM-11 | Добавить запись истории вручную для действующего, проданного и отсутствующего авто; передать пустое имя, неположительный пробег/стоимость и пустые необязательные строки | Создаётся запись только для действующего авто с непустым именем и положительным пробегом; имя обрезано, пустые тексты и неположительная стоимость становятся `null`; запись не меняет работу |
| DOM-12 | Определить вид госномера для российских, европейских, американских и нераспознанных форматов с разными регионами устройства | Выбирается согласованный `PlateStyle`; мягкая проверка не запрещает сохранить введённый номер |
| DOM-13 | Выбрать иконку для новой и старой работы; прочитать неизвестное имя и `NULL` из хранилища | Выбранная иконка сохраняется; новая работа получает `WRENCH`; старой без выбора остаётся `null`; неизвестное имя безопасно отображается как отсутствие иконки |
| DOM-14 | Скрыть и показать госномер и VIN машины | Флаги меняются независимо друг от друга и не затрагивают остальные поля машины |
| DOM-15 | Выбрать машину при запуске: «открывать по умолчанию» включено/выключено, машина удалена, ничего не открывалось; удалить выбранную или последнюю открытую машину | Открывается выбранная, последняя открытая машина или список; ссылки в настройках сбрасываются или заменяются по правилам `ForgetCarInSettingsUseCase` |
| DOM-16 | Удалить машину с историей и без, полностью удалить проданную; собрать общую историю | Машина с историей становится проданной без работ, без истории — удаляется; полное удаление убирает всё; общая история — новые сверху, записи отсутствующих машин не показываются |

### 3.2 Хранилище и интеграция

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| DATA-01 | Сохранить и прочитать каждую модель, включая `null` поля и настройки по умолчанию | Все поля проходят round-trip без потери и ошибочного преобразования |
| DATA-02 | Проверить мапперы SQL-значений, enum/статусов и дат | Маппинг корректен для всех поддерживаемых значений; неизвестные/повреждённые значения обрабатываются предсказуемо |
| DATA-03 | Подписаться на Flow списка авто, одной машины, истории и настроек; выполнить запись | Наблюдатели получают актуальные данные после изменения и не выдают устаревшее состояние |
| DATA-04 | Отметить/снять выполнение, изменить историю и удалить машину в ходе одной операции | Связанные изменения атомарны: при ошибке нет частично обновлённого состояния |
| DATA-05 | Удалить машину обычным способом и через полное удаление, если эти варианты различаются по спецификации | Удаляются ровно те связанные работы/записи, которые описаны в требованиях |
| DATA-06 | Открыть базу после миграции с каждой поддерживаемой предыдущей версии схемы | Данные сохраняются, схема обновляется без потери; новую установку также можно создать с нуля |
| DATA-07 | Закрыть и повторно открыть приложение после CRUD-операций | Авто, работы, история и настройки остаются сохранёнными |
| DATA-08 | Сохранить и прочитать госномер, вид списка авто, выбранную иконку и ручную запись истории | Новые поля проходят round-trip; ручная запись имеет пустые `task_id` и `prev_*`; миграция версии 3 сохраняет старые данные и даёт `NULL` для старых иконок/номеров |
| DATA-09 | Передать план напоминаний платформенному планировщику, заменить и отменить его | `ReminderSchedulerImpl` ставит ровно запланированные уведомления, снимает устаревшие и не дублирует их; Android — `ReminderWorker`, iOS — локальные уведомления |

Каждую миграцию проверять на копии базы предыдущей версии с реалистичными данными, включая `null`, пустую историю и несколько автомобилей. Если миграций ещё нет, добавить проверку начальной схемы и завести обязательный сценарий на каждую будущую миграцию.

## 4. Security и приватность

### 4.1 Автоматические проверки в CI

На каждый PR запускать:

1. **Сканирование секретов** в изменениях и репозитории: токены, пароли, приватные ключи, provisioning/signing материалы. Подтверждённый секрет блокирует PR; секрет считается скомпрометированным и требует ротации, а не только удаления из текущего diff.
2. **SCA зависимостей** для Gradle-плагинов и runtime/test-зависимостей: блокировать известные критические и высокие уязвимости. Исключение допускается только с обоснованием, владельцем и сроком пересмотра.
3. **SAST/конфигурационный анализ** Kotlin, Swift, Gradle, Android Manifest и iOS plist: блокировать подтверждённые критические/высокие находки, вести проверяемый список исключений.

Повторять полный анализ перед релизной сборкой. Отчёт должен позволять сопоставить найденную проблему с зависимостью/файлом, уровнем риска и решением команды. Если репозиторий CI ещё не настроен, добавить эти проверки в обязательный workflow до включения security-гейта.

### 4.2 Ручные и интеграционные security-проверки

| ID | Проверка | Критерий |
|---|---|---|
| SEC-01 | Установить release-сборку и проверить Android manifest после merge ресурсов | Экспортирован только необходимый launcher-компонент; нет случайно открытых сервисов/receiver/provider |
| SEC-02 | Проверить сетевые настройки Android и iOS | Нет разрешения cleartext-трафика или ослабления ATS без документированной необходимости; приложение не отправляет локальные данные по сети |
| SEC-03 | Вводить в текстовые поля кавычки, SQL-подобные строки, управляющие символы, Unicode и длинные строки | Нет SQL-инъекции, падения, повреждения других записей или выхода данных за пределы UI; значение безопасно отображается/отклоняется согласно валидации |
| SEC-04 | Искать VIN, марку, историю и стоимость в logcat/Xcode logs, crash diagnostics и сообщениях об ошибках | Пользовательские данные не попадают в диагностические логи без явного согласия/обоснования |
| SEC-05 | Проверить backup/restore Android и резервное восстановление iOS на тестовых данных | Резервная копия и восстановление ведут себя по принятой политике; база не повреждается, секреты подписи и отладочные данные в резервную копию не попадают |
| SEC-06 | Проверить хранение локальной БД в sandbox и доступ другого приложения | Данные доступны только в sandbox приложения и через штатные механизмы резервного копирования ОС |
| SEC-07 | Запустить приложение после отказа/отзыва разрешений уведомлений и с ограниченной фоновой работой | Нет обхода системного разрешения, аварийного завершения или бесконечных повторных запросов |
| SEC-08 | Проверить release артефакт и настройки сборки | В release нет debug-only компонентов/логирования и тестовых данных; подпись выполняется штатной конфигурацией без включения ключей в репозиторий |

Политика хранения и резервного копирования данных, найденные риски и их проверка перед релизом описаны в локальной спецификации безопасности, которая в репозиторий не входит. Здесь — только общие проверки. Поведение резервного копирования должно быть понятно пользователю из политики приватности.

Пройти поток на физическом Android и iPhone.

## 6. Порядок запуска и критерии релиза

- Каждый PR: сборка затронутых targets, весь `commonTest`, Android host tests, Android/iOS компиляция, доступные UI tests и три security-сканера. Новый подтверждённый high/critical риск или падение обязательного теста блокирует merge.
- Перед релизом: весь автоматический набор на обеих платформах, миграции на предыдущей поддерживаемой схеме, backup/restore и физический smoke на двух устройствах.
- Падение допустимо только для явно помеченного нестабильного теста с заведённым дефектом, владельцем и сроком исправления; security-гейт нельзя обходить без задокументированного исключения.
- Критические потоки без пропусков: сохранность локальных данных, корректное вычисление статуса, выполнение/отмена ТО, удаление, настройки и пользовательские разрешения.
- Вести результаты по ID сценариев: pass/fail/blocked, платформа и версия ОС, версия сборки, ссылка на дефект/отчёт. Целевой процент покрытия кода не устанавливать до появления стабильного baseline; измерять покрытие domain-логики отдельно и расширять его без подмены поведенческих критериев.
