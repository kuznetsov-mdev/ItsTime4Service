# Экспорт и импорт для версии 1.1.0

**Черновик. Первая итерация анализа от 06.11.2026. Требования не утверждены.**

Документ подготовлен мобильным аналитиком. Источники — принятые решения пользователя в текущем обсуждении, общий план в `dev_plan.md` и фактический код проекта, проверенный 06.11.2026. Ниже отдельно приведены факты, рекомендации аналитика и вопросы владельцу продукта. Код, схема БД, макет и действующие спецификации в этой итерации не изменяются.

## 1. Цель и уже принятые ограничения

Пользователь должен уметь перенести собственные данные на другое устройство и передать другому владельцу подготовленный регламент, не передавая свою личную историю. Функция предназначена в том числе для людей, слабо разбирающихся в обслуживании автомобилей.

Принято пользователем:

- Версия 1.1.0 посвящена экспорту/импорту. Общий план: [dev_plan.md](../../dev_plan.md), раздел «План обновлений после первого релиза».
- Предусмотрены две разные операции: полная резервная копия собственных данных и отдельный обмен регламентом.
- Полная копия переносит автомобили, пробег, работы, историю и настройки.
- Передаваемый другому владельцу регламент не включает VIN, госномер, текущий пробег, личную историю, расходы и факты последнего обслуживания отправителя. В нём нужны работы, интервалы, применимость к модификации, условия эксплуатации и доступные источники.
- Нужны предварительный просмотр импорта, выбор назначения и обработка совпадений. Конкретные правила ещё не выбраны.
- Функция работает локально, без обязательных расходов, аккаунта, сервера и собственного облака. Пользователь сам передаёт файл выбранным системным способом.
- Основной магазин — RuStore для Android; iOS остаётся поддерживаемой платформой KMP. Одновременный пользовательский выпуск новой функции на обеих платформах требует отдельного решения.
- До кода соблюдается порядок: макет → спецификация → согласование → реализация.
- Помощь новичку и неизвестная история запланированы на 1.2.0, прогноз пробега — на 1.3.0, ИИ — на 1.4.0. Импорт не должен выдавать неизвестное обслуживание за известное.

## 3. Предлагаемый scope первой версии

Ниже рекомендации аналитика, ожидающие ответов на вопросы раздела 8.

| Операция | Рекомендуемая граница 1.1.0 | Более сложный вариант |
| --- | --- | --- |
| Создать резервную копию | Полный снимок всех собственных данных одним файлом по явному действию | Выбор отдельных автомобилей с историей, регулярное автоматическое копирование |
| Восстановить копию | Предпросмотр, осознанная полная замена после подтверждения; до записи возможность сохранить текущие данные | Объединение двух развивавшихся независимо баз с разрешением конфликтов |
| Поделиться регламентом | Регламент одной выбранной машины, выбор работ, проверка состава без личной истории | Библиотеки нескольких регламентов в одном файле, публичный каталог |
| Применить регламент | К существующему или создаваемому автомобилю, выбор работ, явная обработка совпадений | Автоматическое сопоставление модификаций и фоновые обновления чужого регламента |
| Получить/сохранить файл | Системные действия устройства, понятные названия операций | Собственные облако, аккаунты, синхронизация и ссылки приглашения |

Рекомендация — начать с восстановления полного снимка и переноса одного регламента. Объединение личных баз заметно расширяет требования к идентичности сущностей и разрешению конфликтов. Отсутствие объединения не должно маскироваться: до подтверждения явно показывается, что текущие данные будут заменены.

Вне предлагаемой первой итерации: ИИ, сетевой каталог, фоновая синхронизация устройств, импорт произвольных таблиц сторонних приложений, печатные отчёты, общий редактор характеристик автомобиля. Включение минимальных сопроводительных сведений регламента и неизвестного обслуживания требует отдельных решений Q10–Q11.

| Работы | Названия, интервалы по пробегу/месяцам, последний пробег/дата, индивидуальный порог напоминания, иконки, владельцы и порядок |
| История | Все записи, включая ручные и относящиеся к удалённым работам/проданным машинам; даты, пробеги, стоимость, сервис, комментарии, связи и значения для отмены отметок, порядок |
| Настройки | Все пользовательские настройки и ссылки на автомобили; применение настроек зависит от Q6 |
| Состояние уведомлений | Не переносить задания WorkManager/запросы iOS. Будущий план пересоздавать после успешного импорта. Предлагается сохранить значимые следы уже показанных напоминаний с их связями, чтобы восстановление не вызывало преждевременные повторы |
| Служебная информация файла | Вид файла, версия формата, версия приложения-создателя, время создания и сведения для проверки целостности. Версия формата не тождественна версии БД или приложения |

Данные из папки приложения и секреты сборки в копию не включаются. Системное разрешение на уведомления, пути файлов, содержимое системных буферов и временный UI-state не являются переносимыми пользовательскими настройками. Безопасность файла зависит от Q4, поэтому до согласования нельзя обещать шифрование или защиту паролем.

### Регламент для другого владельца

Включать: выбранные названия работ, интервалы по пробегу и времени, доступные иконки; идентификацию набора и версию формата; согласованные сопроводительные сведения применимости/условий/источников. Индивидуальные пороги напоминаний — по решению Q12.

Исключать автоматически: собственные идентификаторы автомобиля и истории отправителя, VIN, госномер, флаги их скрытия, текущий пробег, даты и пробеги выполнения, записи истории и данные их отката, расходы, сервисы, личные комментарии, настройки запуска/темы/уведомлений и прошлые уведомления.

Названия работ и свободное описание могут содержать введённый человеком текст; автоматическое исключение полей не гарантирует отсутствия личных сведений внутри произвольного текста. Перед отправкой пользователь видит состав и может исправить название/описание. Метка «проверенный регламент производителя» не назначается автоматически: файл может содержать пользовательский набор без подтверждённого источника.

## 5. Пользовательские истории и сценарии

### A. Перенос собственных данных

**История:** как владелец приложения, я хочу сохранить всё обслуживание и восстановить его на другом устройстве, чтобы не заполнять данные заново.

Основной сценарий:

1. Пользователь выбирает создание резервной копии; приложение показывает её состав и согласованный способ защиты.
2. Приложение формирует согласованный снимок. Пользователь сохраняет или передаёт файл через системное действие.
3. На принимающем устройстве пользователь выбирает восстановление и файл; при необходимости вводит пароль.
4. До записи приложение проверяет файл и показывает дату копии, автомобили, объём истории и настройки; отдельно объясняет эффект для существующих данных.
5. После явного подтверждения выполняется согласованная операция восстановления; при ошибке текущие данные остаются целыми.
6. Приложение показывает итог, пересчитывает отображаемые статусы на текущую дату и перестраивает уведомления с учётом разрешений устройства.

Альтернативы: пустая принимающая база; база уже заполнена; файл повторно открывается; в копии только проданные автомобили; копия содержит полностью пустой набор; сохранение настроек получателя. Для намеренного восстановления пустой копии поверх непустой базы требуется отдельное явное подтверждение замены; ошибочный пустой/повреждённый файл не считается валидной пустой копией.

### B. Обмен регламентом

**История:** как владелец, уже составивший список работ, я хочу передать подходящий набор другому владельцу, чтобы ему не приходилось повторять ввод.

Основной сценарий:

1. Пользователь выбирает автомобиль и действие передачи регламента.
2. Проверяет/выбирает работы и доступные сведения о применимости, затем видит состав отправляемого набора без личной истории.
3. Сохраняет или передаёт файл системным способом.
4. Получатель открывает файл, читает применимость/условия/источник и выбирает целевой автомобиль либо создаёт новый.
5. Получатель выбирает работы; приложение показывает совпадения и согласованные варианты их обработки.
6. Последнее обслуживание заполняется только из сведений получателя; если неизвестно — применяется решение Q10.
7. Перед подтверждением показывается, какие работы добавятся/изменятся, какие пропускаются. После подтверждения нет вымышленных записей истории.

Альтернативы: у получателя пока нет автомобилей; регламент неприменим к его модификации; работы уже присутствуют с другими интервалами/именами; повторный импорт того же файла; получатель использует другие единицы или язык; выбранная машина удалена во время предпросмотра. Импорт сохраняет текст названий, а не обещает автоматический перевод; числовые интервалы передаются в однозначных базовых единицах и отображаются в выбранных единицах получателя.

### C. Ошибки и отмена

- Отмена выбора/сохранения файла — обычное завершение без сообщения об ошибке и без изменения данных.
- Недоступный файл, неверный пароль, повреждённый файл, неподдерживаемый тип/версия, превышение допустимого размера, недопустимые значения и нарушенные обязательные связи различаются понятными сообщениями.
- При ошибке проверки импорт не начинается; при ошибке записи откатывается вся операция. Частично пропавшая история или часть импортированных работ не допускаются.
- При отказе системного провайдера сохранить/передать файл нельзя сообщать «копия сохранена» или «получатель получил файл». Формирование файла, сохранение у провайдера и передача получателю — разные результаты.
- Изменение исходных данных после предпросмотра не должно приводить к записи по устаревшему плану: требуется актуализация/повторная проверка перед подтверждением.
- Убийство процесса и ошибка уведомлений после завершённого импорта не должны провоцировать повторное добавление сущностей при повторном открытии приложения.

## 6. Предлагаемые критерии приёмки

Это проверяемые ориентиры для второй итерации; окончательные формулировки зависят от ответов Q1–Q14.

1. Полная копия после восстановления сохраняет автомобили, порядок, работы, историю, связи и допустимое поведение отмены выполненной работы. Проверка включает проданную машину и историю уже удалённой работы.
2. При экспорте регламента в структуре файла отсутствуют исключённые личные поля. Импорт не создаёт чужой факт обслуживания или историю получателя.
3. При одинаковом фактическом состоянии данных и текущей дате после восстановления статусы совпадают с расчётом до экспорта; устаревший статус из файла не используется как источник истины.
4. Ошибка любого этапа до завершения записи не оставляет частичный результат и не повреждает прежнюю базу.
5. Повторное открытие/нажатие подтверждения не создаёт неконтролируемых копий; правила совпадений проверены отдельно для полного восстановления и шаблона.
6. Поддерживаемые файлы одинаково читаются на согласованных платформах и при RU/EN/ES, километрах/милях, разных локалях даты.
7. Формат версии выше поддерживаемой не импортируется молча с потерей неизвестных данных; пользователь получает действие «обновить приложение». Поддержка старых форматов и необязательных расширений явно описывается в контракте.
8. Системные права на уведомления не переносятся из файла; очередь пересоздаётся на принимающем устройстве, не остаётся уведомлений о заменённых машинах.
9. При отмене системного диалога нет ложной ошибки/ложного успеха; при отказе сохранения или отсутствии места результат объясняется без потери существующих данных.
10. Операции доступны без регистрации и собственной сети приложения; приватные данные не отправляются за пределы устройства иначе как выбранным пользователем системным действием.

## 7. Предложения команде без дополнительных продуктовых вопросов

Это не утверждённый проект реализации. Рекомендации вынесены отдельно, чтобы не заставлять владельца выбирать технические детали.

- Использовать переносимую логическую структуру данных со своей версией формата вместо передачи открытого SQLite-файла. Общий сериализатор/валидатор — в KMP, доступ к документам и системной передаче — в платформенных адаптерах. Конкретные API и библиотеку выбрать при техническом проектировании.
- Рекомендуемое представление — структурированный документ UTF-8 с явным признаком backup/regimen, разными понятными названиями/расширениями файлов, ограничениями размера и количества сущностей. Если выбрано шифрование, способ упаковки и метаданные предпросмотра описать отдельно. Расширение и checksum не заменяют валидацию и не доказывают авторство.
- При полном замещении сохранять идентичность и порядок сущностей. При применении регламента создавать сущности получателя; технический идентификатор набора помогает узнавать повторный импорт, но не становится идентификатором автомобиля отправителя.
- Подготовку снимка и применение импорта выполнять согласованно с последовательным доступом к БД, отдельной транзакционной операцией. Нельзя собирать «полную» копию из независимых Flow-значений, которые могут принадлежать разным моментам времени.
- Валидировать обязательные ссылки на автомобили, принадлежность существующей связанной работы машине, уникальность идентификаторов и диапазоны чисел/дат. Штатную историю удалённых работ допускать; не удалять её автоматически ради «исправления» ссылки.
- Для регламента не делать автоматическое обновление всех совпавших работ только по имени. Предпросмотр даёт человеку контроль; точные правила сопоставления зависят от Q9.
- Данные и очередь ОС восстанавливаются разными средствами. Ошибка пересоздания уведомлений после успешной транзакции БД должна оставлять данные восстановленными и предлагать повторить настройку уведомлений, не повторять весь импорт.
- Системные файлы, незавершённые передачи и временные документы не считать постоянным хранилищем. Срок хранения временных файлов, очистку и пределы памяти согласовать при техническом проектировании с правилами проекта. Исходный пользовательский файл не удалять.
- Детали экранов, навигации, выбора файлов, доступности и подписей передать мобильному дизайнеру после ответов. На этапе реализации проверить ограничения Android/iOS по актуальной официальной документации; в этой итерации платформенные API не выбирались и внешнее исследование не проводилось.

## 8. Вопросы владельцу продукта

Для ответа достаточно номера вопроса и варианта. Рекомендация аналитика не считается ответом пользователя.

### Важные для фиксации scope и сценариев

**Q1. На каких платформах полностью реализуем экспорт/импорт в 1.1.0?**

- **А — Android и iOS с взаимным переносом файлов (рекомендую).** Соответствует назначению KMP; потребуются проверка обоих системных файловых сценариев и тесты Android ↔ iOS.
- Б — пользовательская функция только Android; переносимый формат с расчётом на iOS позже. Меньше объём первой поставки, но перенос на iPhone пока невозможен.

**Q2. Что делать при восстановлении полной копии в уже заполненном приложении?**

- **А — полная замена после предпросмотра и явного подтверждения (рекомендую для 1.1.0).** Результат точно соответствует снимку; прежние данные предварительно можно сохранить по решению Q5.
- Б — предложить и замену, и объединение с текущими данными. Потребуются отдельные правила конфликтов автомобилей, истории и независимо изменённых копий.
- В — разрешать восстановление только в пустое приложение. Самый узкий вариант, но неудобен для исправления ошибок и восстановления на текущем устройстве.

**Q3. Нужен ли уже в 1.1.0 перенос одной своей машины вместе с её личной историей?**

- **А — пока достаточно полной копии всех данных и отдельного обезличенного регламента (рекомендую).** Сохраняются две понятные операции.
- Б — добавить выбор собственных машин с историей. Появляется частичный личный перенос и нужно решить, как он совмещается с данными получателя.

**Q4. Как защищать файл полной резервной копии?**

- **А — защита паролем включена по умолчанию, пользователь может явно сохранить без неё (рекомендую).** Удобно передавать копию; для незащищённой копии нужно понятное предупреждение о VIN, номерах и истории. Потерянный пароль восстановить нельзя.
- Б — обязательный пароль для любой полной копии. Меньше случайно открытых копий, но дополнительный барьер и риск забыть пароль.
- В — в 1.1.0 без пароля, с предупреждением перед сохранением. Меньше scope, но содержимое доступно тому, кто получил файл. Для обычного регламента отдельная защита по умолчанию не предлагается, поскольку личные поля исключаются.

**Q5. Нужна ли обязательная страховочная копия перед полной заменой текущих данных?**

- **А — предложить сохранить текущую копию, разрешить явно продолжить без неё (рекомендую).** Защита от случайной потери без обязательного дополнительного файла при каждом переносе.
- Б — не выполнять замену, пока текущая копия не сохранена. Сильнее защита, но восстановление может блокироваться отказом/недоступностью файлового провайдера.

**Q6. Как применять настройки из полной копии?**

- **А — отдельный переключатель «Восстановить настройки», включён по умолчанию (рекомендую).** Пользователь может оставить тему, единицы и настройки напоминаний принимающего устройства.
- Б — всегда восстанавливать настройки вместе с данными.
- В — восстанавливать только данные, настройки принимающего устройства сохранять всегда. Системное разрешение на уведомления не переносится при любом варианте; включённые напоминания работают только с разрешением принимающего устройства.

**Q7. Куда разрешить применять полученный регламент?**

- **А — к существующей машине или к новой машине, созданной в этом же сценарии (рекомендую).** Покрывает владельца с уже заведённым авто и первое использование приложения.
- Б — только к существующей машине. Создать её нужно заранее обычной формой.

**Q8. Нужен ли выбор отдельных работ при передаче и применении регламента?**

- **А — выбор и при экспорте, и при импорте; изначально выбраны все работы (рекомендую).** Получатель может взять только подходящую часть, отправитель — поделиться выбранными работами.
- Б — экспортировать весь регламент, выбирать работы только при импорте. Проще действие отправителя.
- В — передавать и применять только набор целиком. Меньше UI, но хуже контроль неподходящих/повторяющихся работ.

**Q9. Как поступать с работой, похожей на уже имеющуюся у получателя?**

- **А — показать совпадение, по умолчанию пропустить; разрешить явно заменить параметры выбранной работы, сохранив собственные сведения о выполнении и историю (рекомендую).** Импорт не меняет факты обслуживания.
- Б — только пропускать совпадения, менять интервалы потом вручную.
- В — разрешить добавить отдельную работу-копию. Нужно явно обозначить риск двойного учёта; автоматическое дублирование не предлагается.

**Q10. Что делать с импортированной работой, если последнее обслуживание неизвестно?**

- **А — перенести минимальную поддержку «Не знаю» и рекомендательного статуса из 1.2.0 в 1.1.0 (рекомендую).** Пользователь добавит регламент без вымышленного пробега/даты; полноценная помощь новичку остаётся в 1.2.0.
- Б — до сохранения каждой импортируемой работы обязательно вводить собственный известный пробег последнего обслуживания и дату для временного интервала. Неизвестные работы пока не сохраняются; серьёзный барьер для новичка.
- В — в 1.1.0 выпустить личную резервную копию, а применение чужого регламента перенести на 1.2.0. Меняет выбранный приоритет передачи регламентов. Подстановка нуля или текущего пробега без факта выполнения не предлагается.

**Q11. Как описывать применимость и условия регламента, пока в автомобиле нет структурированного профиля?**

- **А — в 1.1.0 необязательные сопроводительные сведения: описание модификации, условия и источник; структурированный профиль — в 1.2.0 (рекомендую).** Требуется хранить и показывать эти сведения, не теряя их при передаче дальше. При отсутствии источника набор обозначается пользовательским.
- Б — уже в 1.1.0 добавить отдельные поля года, двигателя, коробки, рынка и условий эксплуатации. Больше scope, но появляется основа строгой проверки применимости.
- В — в 1.1.0 передавать только работы и интервалы, сведения о применимости добавлять позже. Это временно сокращает принятый состав регламента и требует явного согласия.

**Q12. Чей порог «Напоминать за …» использовать для новых работ из чужого регламента?**

- **А — значение по умолчанию получателя; не переносить личный порог отправителя (рекомендую).** Поведение соответствует настройкам получателя; собственный порог существующей совпавшей работы сохраняется.
- Б — переносить индивидуальный порог каждой работы из файла.
- В — предложить получателю выбор при импорте. Больше контроля, но ещё одно решение для новичка. Заводские интервалы обслуживания от этого выбора не меняются.

### Вопросы о расширении первой версии, которые можно отложить

**Q13. Нужен ли в 1.1.0 отдельный отчёт для чтения без приложения?**

- **А — пока только файл переноса, читаемый самим приложением; PDF/таблицы позднее (рекомендую).** Удобная передача файла и обмен данными решаются в первой версии.
- Б — добавить читаемый отчёт уже в 1.1.0, например для сервиса. Потребуется отдельно выбрать состав, формат и правила исключения личных данных; отчёт не заменяет восстанавливаемую копию.

**Q14. Создание копии в 1.1.0 только вручную или также автоматически?**

- **А — вручную по действию пользователя (рекомендую).** Пользователь выбирает место сохранения и способ защиты; авто-копирование проектируется позже отдельно.
- Б — добавить напоминание о необходимости создать копию, без фонового сохранения.
- В — сразу автоматические копии. Понадобятся отдельные решения о месте, частоте, количестве, защите и доступе к файлам на каждой платформе; собственное облако при этом всё равно не требуется.
